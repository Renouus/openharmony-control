# 智能家居控制系统技术说明

## 1. 项目概述

本项目实现了一个面向智能家居场景的控制系统原型，目标是提供一个可演示、可扩展、具备前后端协同能力的家庭中控方案。系统包含移动端控制界面、控制中心服务、共享设备契约三部分，通过统一接口和数据模型实现设备状态展示、远程控制、场景联动、命令记录、异常演示与实时同步。

从定位上看，本项目不是单纯的页面展示，而是一个完整的数据闭环系统。用户在前端发起操作后，系统会经过接口调用、命令签名校验、设备状态更新、数据库版本推进、WebSocket 广播和前端状态回写，最终完成界面刷新。因此，本项目的核心价值不仅在于界面功能完整，还在于其清晰的系统架构与完整的数据流设计。

## 2. 系统总体架构

系统整体采用三层协同架构：

1. OpenHarmony ArkTS 前端应用层
负责页面展示、用户交互、状态渲染和本地缓存，承载首页、门禁、摄像头、空调、家庭、自动化、通知等业务页面。

2. Fastify 控制中心服务层
负责设备注册、状态汇总、命令执行、场景管理、同步接口、WebSocket 推送和安全校验，是系统的业务中枢。

3. 共享设备契约层
位于 `packages/device-contract`，负责定义前后端共享的数据类型、命令结构、设备能力和安全信封结构，用于保证接口语义一致。

整体关系可以概括为：

`ArkTS UI -> Repository -> DeviceApi -> Fastify Routes -> Registry / DB / Simulator -> HTTP / WebSocket -> ArkTS UI`

这种架构的优点是职责清晰、耦合度低、便于测试，并且方便后续将“模拟设备”替换为真实 IoT 接入层。

## 3. 项目目录与模块划分

项目主要由以下三个核心目录组成：

- `apps/openharmony-control`
  OpenHarmony 前端应用，采用 ArkTS 编写，负责界面、交互、本地缓存和页面状态管理。

- `services/control-center`
  控制中心后端，基于 Fastify 构建，负责 API、命令执行、场景联动、同步服务、WebSocket 推送和数据库访问。

- `packages/device-contract`
  共享契约包，定义 `DeviceDescriptor`、`DeviceState`、`DeviceCommand`、`SceneDescriptor`、`SignedCommandEnvelope` 等前后端共用类型。

这种拆分方式使系统形成“界面层、业务层、契约层”分离的结构，前后端不直接依赖彼此的内部实现，而是通过共享类型与标准接口协作。

## 4. 前端架构设计

### 4.1 分层结构

前端并不是把所有逻辑堆积在页面中，而是采用了比较清晰的分层结构：

- `pages`
  页面入口与整体装配，例如 `Index.ets` 负责顶层页面切换与依赖注入。

- `views` / `components`
  负责界面展示和用户交互，不直接访问底层网络。

- `controllers`
  负责跨页面编排和动作触发，例如 `AppController` 负责页面刷新、命令触发和业务协调。

- `viewmodel`
  面向单一业务域封装用例，例如家庭、灯光、门禁、气候等。

- `services`
  封装 HTTP 接口访问、WebSocket 连接、本地数据库访问和仓储逻辑。

- `model`
  保存视图状态对象、映射函数、导航状态和领域辅助模型。

### 4.2 前端核心设计思想

前端采用 `View -> Controller/ViewModel -> Repository -> API/Local DB` 的结构，主要目的有三个：

1. 页面组件只关注展示与交互，避免把网络逻辑写进 UI。
2. 业务逻辑集中在 `ViewModel` 和 `Repository`，便于单元测试和复用。
3. 本地缓存、远程同步、实时推送都统一收口在 `Repository` 层，避免数据来源分散。

### 4.3 页面组织方式

前端主入口 `Index.ets` 负责应用级状态、标签页切换和子页面导航。主标签页包括首页、自动化、通知、家庭等；子页面包括灯光、门禁、摄像头、空调、场景编辑、房间编辑等。这样做的意义在于：

- 顶层页面切换逻辑统一；
- 业务状态集中管理；
- 页面之间共享同一套控制器和应用状态快照；
- 后续扩展新页面时不需要重构已有页面。

## 5. 后端架构设计

### 5.1 控制中心的职责

后端 `services/control-center` 不是简单的数据转发层，而是整个系统的控制中枢，主要负责：

- 暴露 REST API；
- 聚合设备状态并生成首页摘要；
- 执行设备命令；
- 维护场景与自动化规则；
- 提供增量同步接口；
- 提供 WebSocket 实时推送；
- 维护命令历史；
- 支持演示故障注入；
- 执行命令签名与重放保护。

### 5.2 路由模块化

后端通过 `buildApp()` 注册多个业务路由模块，包括：

- `devices`
- `access`
- `camera`
- `family`
- `climate`
- `commands`
- `scenes`
- `automations`
- `rooms`
- `sync`
- `websocket`
- `demo`

每类业务使用独立路由文件管理，优点是边界清楚、职责单一、便于扩展。例如要增加新的家庭业务，不需要改动设备控制路由；要扩展同步机制，也可以集中在 `sync` 和数据库服务中演进。

### 5.3 模拟设备层

后端内部引入了设备注册表和模拟器适配层，例如门锁、灯光、空调等设备都有对应的设备对象或模拟执行器。这样一来，项目在不依赖真实硬件的情况下，也能形成完整的命令执行闭环，满足原型验证和答辩演示的需要。

## 6. 共享数据契约设计

为了避免前后端对同一业务对象理解不一致，项目通过 `packages/device-contract` 抽出共享契约层。该层定义了系统中的关键数据模型：

- `DeviceDescriptor`：设备基础描述
- `DeviceState`：设备运行时状态
- `EnhancedDeviceDescriptor`：增强设备展示模型
- `DeviceCommand`：设备命令结构
- `CommandHistoryEntry`：命令历史记录
- `SceneDescriptor`：场景定义
- `SceneRunResult`：场景执行结果
- `SignedCommandEnvelope`：签名命令信封

共享契约层的价值在于：

1. 前后端使用统一的类型语义；
2. 降低接口变更导致的联调成本；
3. 提升系统可维护性和可测试性；
4. 为后续接入更多客户端提供稳定协议基础。

## 7. 核心接口设计

项目当前的核心接口可以分为六类：

### 7.1 设备与首页摘要接口

- `GET /api/devices`
- `GET /api/devices/:deviceId`
- `GET /api/summary`

用于支撑首页概览、设备列表和详情展示。

### 7.2 命令控制接口

- `POST /api/demo/sign-command`
- `POST /api/commands`
- `GET /api/commands/history`

用于完成设备控制、签名封装、命令校验和历史回显。

### 7.3 场景与自动化接口

- `GET /api/scenes`
- `POST /api/scenes`
- `PUT /api/scenes/:sceneId`
- `DELETE /api/scenes/:sceneId`
- `POST /api/scenes/:sceneId/run`
- `GET /api/automations`

用于场景配置、执行和自动化规则展示。

### 7.4 领域功能接口

- `GET /api/access`
- `POST /api/access/guest-keys`
- `GET /api/cameras`
- `PUT /api/cameras/:cameraId`
- `GET /api/family`
- `POST /api/family/broadcast`
- `GET /api/climate`
- `PUT /api/climate`

用于门禁、监控、家庭、空调等垂直功能页面。

### 7.5 同步接口

- `GET /api/sync?lastVersion=...`

用于前端从后端拉取按版本号增量变化的数据，包括设备、房间、场景、自动化四类实体。

### 7.6 实时推送接口

- `GET /ws/events`

用于服务端主动广播设备状态变化，实现实时刷新体验。

## 8. 数据流转设计

本项目的数据流不是单一方向，而是根据业务划分为四条主链路：读取链路、控制链路、同步链路、实时链路。

### 8.1 读取链路

读取链路主要用于页面加载和状态展示，其过程如下：

1. 用户打开某个页面；
2. `View` 调用控制器或视图模型；
3. `ViewModel` 调用 `SmartHomeRepository`；
4. `Repository` 先读取本地 SQLite 缓存；
5. 如果缓存为空，则调用 `DeviceApi` 请求后端；
6. 后端返回数据后写入本地数据库；
7. 前端将数据映射为页面状态对象并渲染 UI。

这个过程体现了“本地优先、远程补充”的设计思想，保证了首屏速度和离线容错能力。

### 8.2 控制链路

控制链路用于设备操作和业务命令执行，其过程如下：

1. 用户在前端点击开关、门锁、空调或场景执行按钮；
2. `View` 将动作交给 `Controller`；
3. `Controller` 调用对应 `ViewModel`；
4. `ViewModel` 调用 `Repository.sendDeviceCommand()` 或 `runScene()`；
5. `DeviceApi` 先调用 `/api/demo/sign-command` 生成签名信封；
6. 前端再将签名命令发送到 `/api/commands`；
7. 后端执行签名验证、重放保护、设备查找和模拟器执行；
8. 执行结果写入数据库与命令历史；
9. 后端广播更新事件；
10. 前端接收事件后刷新本地状态和界面。

因此，本项目中的控制行为并不是“前端改一个变量”，而是经过了一次完整的服务端业务处理流程。

### 8.3 同步链路

同步链路用于保证前端本地缓存与服务端状态最终一致，其过程如下：

1. 前端持有一个 `lastVersion`；
2. `Repository.performBackgroundSync()` 调用 `/api/sync?lastVersion=n`；
3. 后端通过 `DatabaseService.getSyncData(lastVersion)` 查询版本号大于 `n` 的变化数据；
4. 后端返回 `devices`、`rooms`、`scenes`、`automations` 以及 `currentVersion`；
5. 前端通过 `DomainEventAdapter` 将同步结果转换为统一领域事件；
6. `DatabaseEventProcessor` 作为唯一写入者把变化写入本地数据库；
7. `SyncDao` 更新本地最后同步版本；
8. 页面再次读取本地数据并完成刷新。

这种设计的关键是：前端不会直接把远端响应散落写入多个地方，而是通过统一事件适配和统一写入器保证一致性。

### 8.4 实时链路

实时链路用于设备状态变化后的即时刷新，其过程如下：

1. 前端启动时建立 WebSocket 连接；
2. 后端将连接注册到客户端连接表；
3. 当命令执行、场景运行、故障注入等行为导致设备状态变化时，后端调用 `broadcastEvent()`；
4. 后端通过 `/ws/events` 将 `DeviceStateUpdated` 等事件广播到前端；
5. 前端 `WebSocketClient` 接收消息；
6. `DomainEventAdapter` 解析消息并转换为领域事件；
7. `DatabaseEventProcessor` 写入本地数据库；
8. 页面通过状态刷新机制反映最新结果。

实时链路的作用是减少前端轮询，提高交互反馈速度，使系统表现更接近真实中控系统。

## 9. 本地缓存与一致性机制

本项目在前端引入 SQLite 本地缓存，主要缓存设备、房间、场景和同步元数据。这样做的原因有三点：

1. 首次加载后可以快速复用本地数据；
2. 后端短时不可用时仍能显示最近一次同步结果；
3. 为同步和实时事件提供统一落库入口。

为了避免并发写入导致的数据错乱，项目引入了两个关键机制：

- `DomainEventAdapter`
  将 WebSocket 与 Sync API 的数据统一转换为领域事件。

- `DatabaseEventProcessor`
  作为唯一写入者处理所有本地数据库变更，避免多个模块直接竞争写库。

这意味着系统在设计上已经考虑了“远程同步”和“实时推送”同时到达时的一致性问题。

## 10. 安全机制设计

尽管本项目以演示原型为主，但命令链路仍加入了较完整的安全设计。

### 10.1 HMAC 命令签名

前端不会直接裸发控制命令，而是先请求 `/api/demo/sign-command`，由服务端基于共享密钥生成签名信封，再通过 `/api/commands` 提交执行。

### 10.2 重放保护

后端在验签时结合 `nonce` 和时间窗口进行重放保护，避免同一份命令被重复提交。

### 10.3 强制未授权演示

项目提供 `POST /api/demo/faults/security`，可强制进入“命令未授权”演示模式，用于说明系统具备异常处理与安全反馈机制。

### 10.4 HTTPS 预留能力

当设置 `TLS_CERT_PATH` 与 `TLS_KEY_PATH` 时，控制中心可切换到 HTTPS 监听模式，说明架构上已经为更安全的部署方式预留了空间。

### 10.5 HTTPS 预留能力
传输层，通信链路加密，防御中间人攻击，TLS 1.3 + 证书固定（Certificate Pinning）

### 10.6 HTTPS 预留能力
数据层，业务载荷端到端加密，双重防护，AES-256-GCM（12B IV + 16B AuthTag）+ HMAC-SHA256 + 重放防护

### 10.7 HTTPS 预留能力
密钥层，硬件级密钥管理，密钥不出安全环境，OpenHarmony HUKS（@ohos.security.huks）+ ECDH 协商 + 密钥轮换

## 11. 技术亮点与可扩展性

本项目的技术亮点主要体现在以下几个方面：

### 11.1 分层明确

前端采用 View、Controller、ViewModel、Repository、Service 分层；后端采用路由模块化和业务组件分离；共享契约独立成包。这使得系统结构清晰，后续维护成本较低。

### 11.2 数据链路完整

项目同时具备读取、控制、增量同步、实时推送四条链路，能够体现一个完整业务系统的核心能力，而不仅仅是静态演示页面。

### 11.3 前后端类型一致

通过共享契约包统一设备模型、命令模型、场景模型和安全信封结构，有利于减少接口不一致问题。

### 11.4 具备离线与增量同步意识

通过 SQLite、本地版本号、同步接口和统一写入器机制，系统已经具备了面向真实业务系统演进的能力。

### 11.5 便于扩展到真实设备

当前设备通过模拟器实现，但控制链路、命令结构、状态同步和前端展示层已经具备稳定边界，未来只需替换设备适配层即可接入真实 IoT 设备。

从工程角度看，本项目的重点不只是“做出了几个页面”，而是构建了一套清晰的中控系统骨架。它已经具备以下特征：

- 具备明确的前后端边界；
- 具备统一的数据契约；
- 具备完整的数据流转链路；
- 具备一定的安全机制；
- 具备离线缓存与最终一致性思路；

因此，本项目既能够满足原型演示需求，也具备较好的工程化延展能力。
