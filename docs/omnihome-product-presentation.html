Needs & Scenarios

需求场景分析

在真实家庭场景中，用户并不缺设备，而是缺少一个统一、可靠、可联动的控制入口。 OmniHome 关注的不只是“连上设备”，而是让状态、命令和反馈形成完整体验。

面向课程答辩与原型展示，我们将核心问题拆解为入口统一、状态感知、联动执行和家庭协同四类场景。
01

设备入口分散

灯光、门锁、摄像头和空调往往来自不同入口，用户需要频繁切换页面甚至切换应用。

02

状态信息割裂

单个页面能看到局部状态，但无法快速判断全屋设备、环境与风险提示的整体态势。

03

控制反馈滞后

只完成按钮请求远远不够，系统还需要处理验签、执行、回写、广播与历史留痕。

04

联动能力薄弱

家庭场景真正需要的是场景与自动化，而不是用户重复点击多个设备来完成一次动作组合。

Product Solution

产品整体方案设计

整体方案围绕“一个客户端入口、一个业务控制中枢、一套统一契约、一条可靠状态闭环”展开， 让展示、控制、同步与扩展拥有清晰结构边界。

方案主线

OmniHome 采用 OpenHarmony 客户端 + Fastify 控制中心 + 共享契约层 + SQLite / 设备适配层的组合方案。 它既保留了原型开发的轻量与可验证性，也为后续替换真实 IoT 设备网关与数据服务保留了工程化扩展空间。

  • OpenHarmony 客户端承载统一交互入口与本地视图状态。
  • 控制中心服务负责命令执行、场景调度、历史记录和事件广播。
  • 共享契约层统一设备模型、命令结构与安全信封。
  • SQLite 与设备适配层负责状态来源、持久化与版本同步支撑。
OmniHome 控制中枢

通过统一交互入口整合设备状态读取、命令执行、场景联动、家庭通知与系统演示能力。

OpenHarmony 客户端 总览、门禁、灯光、气候、通知与家庭协同页面。
Fastify 控制中心 设备路由、场景规则、命令签名、历史追踪与 WebSocket 广播。
共享契约层 统一定义设备模型、命令结构、场景定义与安全信封。
SQLite / 适配层 业务数据、版本元数据、模拟设备状态与后续真实适配接口。

Technology & Innovation

技术与创新要点

我们没有把系统做成单纯的静态页面拼装，而是把共享模型、安全命令链路、增量同步与实时广播纳入统一设计主线。

Shared Contract

共享契约驱动前后端一致性

将设备描述、增强快照、命令结构、场景定义与安全信封集中到共享契约包，降低接口演化带来的联调成本。

Secure Command Flow

签名命令链路保障控制安全

控制请求采用“先签名、后执行”的双阶段模式，并结合 nonce 与时间窗口重放保护，适用于门锁等高敏感设备控制。

Incremental Sync

版本驱动的增量同步机制

依托 metadata.global_version 与实体 version 字段，前端仅拉取变化数据，避免全量刷新造成的状态不一致与开销浪费。

Real-time Feedback

WebSocket 实时事件回推

设备变化、场景执行与异常演示通过 WebSocket 主动广播，使控制结果和状态变化能以接近实时的方式回显到界面。

Replaceable Adapter

设备适配层可替换设计

当前采用模拟设备形成完整演示闭环，未来可平滑替换为真实 IoT 网关或驱动适配层，而不破坏上层交互结构。

Demonstrable System

异常演示能力纳入正式方案

离线故障、环境调整与授权拒绝不再是临时调试入口，而是产品演示和答辩展示的重要组成部分。

家庭与通知
