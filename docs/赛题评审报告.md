## 2. 功能逻辑的正确性

### 2.1 严重缺陷

#### 缺陷 1：服务器启动时清空设备表（数据丢失）

**文件**：`services/control-center/src/server.ts:25-27`

```typescript
db.exec(`DELETE FROM devices;`);
```

每次服务器重启时**清空整个 devices 表**，然后重新填充种子数据。用户运行期间添加/修改的设备数据、自定义名称、备注、房间分配**全部丢失**。

**根因**：设计意图是开发/演示环境的"干净启动"，但无任何开关或环境变量保护。

**建议**：仅当表为空时种子填充，或添加 `--seed` / `--reset` 命令行参数。

#### 缺陷 2：Index.ets aboutToAppear 异常静默吞没

**文件**：`apps/openharmony-control/entry/src/main/ets/pages/Index.ets:115-117`

```typescript
} catch (e) {
  // silently handled
}
```

`refreshAll()` 抛出异常时错误被静默吞没，且 `this.isLoading` 永远不设为 `false`，**加载指示器永久旋转**。

#### 缺陷 3：空调/门锁操作失败无用户反馈

**文件**：`ClimateControlView.ets:112-133`，`LockControlView.ets:62-70`

所有 `.then(() => {}).catch(() => {})` 调用在 API 失败时**完全静默**——用户点击后无任何视觉反馈或错误提示。

#### 缺陷 4：`listDevices` 强制全量同步

**文件**：`smart-home-repository.ets:204-223`

每次调用 `listDevices()` 都触发 `performBackgroundSync(true)`（forceFullSync），导致大量不必要的全量数据拉取。结合 `createDevice` → `listDevices` → 全量同步的调用链，每个操作都引发额外的网络开销和本地 DB 写入。

### 2.2 中等缺陷

| # | 缺陷 | 文件 | 行号 |
|---|------|------|------|
| 5 | `SmartHomeRepository` 与 `listDevices` 间的竞态：返回本地缓存同时异步更新 DB | `smart-home-repository.ets` | 204-223 |
| 6 | `DatabaseEventProcessor` 队列处理 fire-and-forget 无重试 | `DatabaseEventProcessor.ets` | 85,90,130 |
| 7 | `toRoomSyncItem` 使用 `updatedAt` 作为 `createdAt`，新建房间创建时间错误 | `domain-event-adapter.ets` | 118 |
| 8 | `SceneCapsuleContainer` 在 UI 组件中直接 `new SceneRunGuard()` 打破依赖注入 | `SceneCapsuleContainer.ets` | 23 |

## 3. 用户体验与界面设计

### 3.1 正面评价

- UI 视觉精美，采用圆角卡片 + 柔和阴影 + 暖色调配色
- WebSocket 实时推送：设备状态变更即时反映，无需手动刷新
- 动画过渡流畅（onTouch 按压反馈、滚动动画）
- 左滑返回手势 + 滚动位置保存 + 退出未保存弹窗
- 已优化：移除编辑器页面重复 AppHeader

### 3.2 严重问题

#### 问题 1：零响应式设计

在所有 `.ets` 文件中搜索 `vpPercent`、`mediaQuery`、`breakpoints`、`onSizeChange`——**零结果**。

全部尺寸均使用固定像素值：
- `ClimateView.ets:110` — 圆形拨盘 320×320、280×280、244×244 px（在 320px 宽手机上直接溢出）
- `ClimateControlView.ets:301` — Stack 高度写死 340px
- 所有编辑器的标题行统一 56px 高度，无弹性布局

**后果**：平板/折叠屏上 UI 缩放异常，小屏手机上温度拨盘裁切。

#### 问题 2：无暗色模式

主题文件 `smart-home-theme.ets` 仅定义硬编码暖色 hex 值（`#FAF5EE` 米色背景、`#C2652A` 橙色主色），无暗色调色板、无主题切换机制、无系统 `colorMode` 感知。

#### 问题 3：零无障碍支持

搜索 `accessibility`、`contentDescription`、`aria-`：**源文件中零结果**。所有按钮、开关、点击区域均无可访问性标签。

#### 问题 4：硬编码的模拟器地址

- `AppController.ets:50`：`const BACKEND_BASE_URL = 'http://10.0.2.2:3443'`
- `smart-home-repository.ets:104`：`ws://10.0.2.2:3443/ws/events`

真机无法连接此地址，需重新编译 HAP 才能部署到物理设备。

## 4. 代码架构与工程质量

### 4.1 正面评价

- **后端模块化优秀**：13 个清晰的目录边界（routes/、automation/、devices/、integrations/tuya/、db/、security/ 等）

`SubPageOverlay()` 构建器（336-512 行）包含 **16 个 if/else 分支**，每个渲染一个完整子页面。同时管理 4 个模态弹层（标题菜单、添加设备、添加/编辑房间）和 10 个 @State 变量。

#### 问题 3：SceneChip 与 SceneCapsuleItem 100% 重复

两个文件 **逐行完全相同**（48 行 vs 49 行），应删除一个并统一引用。

#### 问题 4：ClimateView 与 ClimateControlView ~80% 重复

两个文件渲染相同的 640px 同心圆温度拨盘、+/- 按钮、模式指示器、装饰圆，仅数据读取方式不同（全局 `appState.climate` vs 指定设备 `getDevice()`）。

#### 问题 5：SmartHomeRepository 责任过重（574 行）

同时承担：API 外观、5 个 DAO 管理、WebSocket 客户端生命周期、事件路由、后台同步编排、数据映射器、错误标准化、自动化刷新去重 —— 违反单一职责原则。

#### 问题 6：AppController 接近上帝对象（675 行，~30 个公共方法）

涵盖：视图模型创建、基础设施实例化、全量刷新、主页/照明/门禁/摄像头/气候/自动化/场景/家庭/房间/设备/供应商 共 11 个领域的操作处理程序。

每个方法都重复相同模式：
```typescript
try { const response = await this.http.request(url, options); if (this.isOk(response)) return ...; throw new Error(...); } catch (e) { throw this.mapError(e); }
```

## 5. 性能与稳定性

### 5.1 严重问题

#### 问题 1：WebSocket 事件处理器叠加泄漏

**文件**：`WebSocketClient.ets:28-31`

```typescript
this.ws.on('close', (err, value) => {
  setTimeout(() => this.connect(), 5000);
});
```

每次 `close` 触发：
1. 创建新的 `setTimeout`（timer ID 未保存，无法清除）
2. `connect()` 重新绑定新的 `close` 事件处理器（旧处理器不被移除）
3. 反复断开重连 → 事件处理器叠加 + 多个并发重连定时器

#### 问题 2：WebSocket 无限重连无退避策略

重连间隔固定 5 秒，无递增延迟，无最大重试次数上限。后端永久不可达时无限循环。

#### 问题 3：后端不可达时前端行为异常

当后端不可达时：
- `DeviceApi.fetchSyncUpdates()` 返回 `{ currentVersion: 0, devices: [], ... }`
- 下一个 `sync_completed` 周期中 `refreshAll` 会读到空数据 → **本地缓存可能被清空**

### 5.2 中等问题

| # | 问题 | 文件 | 行号 |
|---|------|------|------|
| 4 | `refreshAll()` 单次执行 12 个独立网络请求 + 2 个 DB 操作，可能引发大量不必要的重渲染 | `AppController.ets` | 93-112 |
| 5 | Index.ets `setTimeout` 100ms 未清理，组件销毁后可能调用 `scrollTo` | `Index.ets` | 563-565 |
| 6 | `ReplayGuard.seen` Map 无大小上限，高流量时可能内存无界增长 | `envelope.ts` | 23 |

## 6. 安全性

### 6.1 正面评价

- **HMAC-SHA256 命令签名**：使用 `crypto.timingSafeEqual` 防时序攻击
- **Nonce 防重放**：5 分钟时间窗口 + ReplayGuard
- **数据库事务**：设备状态更新在事务中原子执行

### 6.2 严重问题

#### 问题 1：硬编码默认密钥（`demo-shared-key`）

**文件**：`app.ts:78`

```typescript
secret = process.env.CONTROL_CENTER_SHARED_KEY ?? "demo-shared-key",
```

未设环境变量时使用弱默认密钥。任何知晓默认密钥的人可伪造 HMAC 签名，绕过命令验证。

**赛题约束**：赛题明确要求"协议传输的安全性兼顾传输层加密、数据层加密和密钥层保护"——默认密钥直接违反密钥层保护要求。

#### 问题 2：API 端点完全无运行时输入校验

所有路由使用 `request.body as SomeType` 模式，编译器信任但运行时**零保护**：

| 文件 | 行号 | 模式 |
|------|------|------|
| `commands.ts` | 50 | `request.body as DeviceCommand` |
| `commands.ts` | 54 | `request.body as Partial<DeviceCommand>` |
| `sync.ts` | 16 | `request.query as { lastVersion?: string }` |
| `rooms.ts` | 27,43 | `request.body as { name?: string; icon?: string }` |

仅有 `access.ts:88` 使用正确的 `isGuestKeyRequest()` 类型守卫。

#### 问题 3：WebSocket 无认证

**文件**：`websocket.ts:35-38`

```typescript
const clientId = query.clientId || `anon-${Date.now()}`;
```

WebSocket 连接仅靠 `clientId` 查询参数标识，无 JWT/Token/签名。代码注释写 "can be upgraded to JWT auth later"，但当前任何知晓端点的人可接收设备状态广播。

#### 问题 4：TLS 传输加密非强制

**文件**：`server.ts:54-66`

TLS 通过环境变量 `TLS_CERT_PATH` / `TLS_KEY_PATH` 可选配置，未提供时回退为明文 HTTP。当前默认运行在 3443 端口上是 HTTP（非 HTTPS）。

赛题明确要求"传输层加密"，但 **TLS 非强制**。

#### 问题 5：数据层加密完全缺失

赛题要求"数据层加密"，但 SQLite 数据库以明文存储所有数据（设备状态、场景配置、自动化规则等）。无任何字段级/表级加密。

#### 问题 6：API 速率限制缺失

全部路由无速率限制。`/api/demo/sign-command` 暴露 HMAC 签名能力且无认证，攻击者可高频调用该端点进行签名 oracle 攻击。

#### 问题 7：`/api/demo/` 端点暴露调试能力

`POST /api/demo/faults/security` 可切换"安全演示模式"，`POST /api/demo/environment` 可篡改传感器读数。这些端点在生产环境中应禁用或加认证保护。

### 6.3 安全问题对照赛题要求

| 赛题要求 | 实现状态 | 详情 |
|---------|---------|------|
| **传输层加密** | ⚠️ 可选 | TLS 需手动配置证书路径，默认不启用 |
| **数据层加密** | ❌ 缺失 | SQLite 明文存储，无加密 |
| **密钥层保护** | ❌ 缺失 | 默认弱密钥，无密钥轮换，无密钥管理 |

### 7.2 优先级排序（按赛题得分影响）

#### 🔴 P0 — 赛题安全要求直接相关（当前几乎不得分）

5. **WebSocket 认证**：添加 JWT 或 HMAC 签名握手
6. **禁用 `/api/demo/` 端点**：添加环境变量开关，生产环境默认关闭

#### 🟡 P1 — 功能完整性

7. **空调湿度调节**：`ac-living-room` / `ac-bedroom` 设备状态加 `humidity_target` 字段 + 后端 `set-target-humidity` 命令
8. **品牌差异化**：在 `adapters/` 目录为 haier/gree/midea 添加独立协议适配器（至少模拟不同响应格式）

#### 🟢 P2 — 工程质量与 UI

9. **提取 SubPageOverlay 路由**：将 Index.ets 16 个分支提取为独立路由组件
10. **合并重复代码**：SceneEditorView/CreateAutomationView 共享基类，ClimateView/ClimateControlView 共享温度拨盘组件
11. **分解上帝对象**：AppController 按领域拆分为 HomeController/LightingController/ClimateController 等
12. **响应式布局**：关键视图（温度拨盘、灯光面板）加媒体查询 / vpPercent
13. **修复静默错误吞没**：所有空 catch 添加日志 + 用户反馈

#### 🔵 P3 — 稳定性

14. **WebSocket 重连**：添加指数退避 + 最大重试次数
15. **服务器启动保护**：`DELETE FROM devices` 添加条件判断
16. **后端优雅关闭**：添加 SIGTERM/SIGINT handler + WebSocket 通知

### 7.3 总体评价

该项目是一个**架构设计良好的智能家居控制系统 Demo**，核心功能（门禁、灯光、温控、环境监测）全部覆盖，自动化引擎和实时推送机制实现完整。后端模块化清晰，自动化子系统经过多轮修复已达到生产级可靠性。

**主要短板在安全层面**：赛题明确要求的传输层加密、数据层加密和密钥层保护三项目前仅有传输层可选手动配置，其他两项完全缺失。这是影响得分的最关键因素。

**代码质量方面**：前端过度膨胀（692 行单文件、70-100% 重复率的组件对）、硬编码值散落各处、错误处理存在多处静默吞没，但这些问题对赛题评分的影响远小于安全缺失。
