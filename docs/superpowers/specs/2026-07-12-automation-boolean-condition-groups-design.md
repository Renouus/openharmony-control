# 自动化布尔条件组设计

## 目标

完善现有自动化规则，使一条规则能够通过全局“和/或”模式组合多个条件，并以可重复的后端集成测试证明：触发条件成立后，运行时会执行动作、产生设备状态副作用，并写入执行日志。

本设计的验证结论限定为后端自动化链路。OpenHarmony `UnitTestBuild` 只用于证明相关 ArkTS 编辑与映射代码可编译，不代表模拟器、真机、HAP 安装或涂鸦云端运行已验证。

## 当前问题

自动化编辑端已经允许 `RoutineDraft.conditions` 保存多个条件，传输层也会把多个条件写入 `triggerJson`。但后端 `toRuntimeTrigger()` 只取归一化结果中的第一条条件，`RuleEvaluator` 因此只评估单个条件。界面所表达的多条件规则与后端实际语义不一致。

现有后端已经具备事件适配、规则加载、规则评估、顺序动作执行、自触发保护、链深限制和 `automation_execution_logs`。本次工作应扩展现有链路，不另建第二套自动化引擎。

## 范围

本次包含：

- 一条规则统一选择“满足全部条件”或“满足任一条件”。
- 跨设备条件读取设备当前状态，而不是只依赖单次事件载荷。
- 历史 `triggerJson` 数组兼容。
- 自动化编辑页、编辑回填和卡片摘要展示组合语义。
- 后端单元、运行时集成和端到端副作用验证。

本次不包含：

- 嵌套条件组、括号或逐条件连接符。
- `NOT` 运算。
- 时间条件与设备或传感器条件混合。
- 时间窗口、持续时长或复杂事件序列。
- 数据库新增列或 schema 版本迁移。
- 模拟器、真机或涂鸦云端运行验证。

## 数据模型与兼容性

新规则的 `triggerJson` 使用条件组对象：

```json
{
  "logic": "all",
  "conditions": [
    {
      "type": "device",
      "deviceId": "door-front",
      "property": "locked",
      "operator": "==",
      "threshold": false
    },
    {
      "type": "device",
      "deviceId": "light-living-room",
      "property": "power",
      "operator": "==",
      "threshold": false
    }
  ]
}
```

`logic` 只允许：

- `all`：所有条件成立，等价于逻辑“和”。
- `any`：任一条件成立，等价于逻辑“或”。

`triggerType` 继续描述唤醒规则的事件类别，不承载布尔组合语义。数据库仍使用现有 `trigger_json` 字段，不新增 `condition_logic` 列。

归一化层必须同时接受新条件组对象和历史数组。历史单条件或多条件数组统一解释为 `logic: "all"`，避免升级后扩大既有规则的触发范围。新建和更新接口应拒绝空条件组、未知逻辑值以及缺少必要字段的条件。

时间规则保持现有独立结构和定时适配器。本轮不允许时间条件与设备或传感器条件混合。

## 前端设计

`RoutineDraft` 增加全局组合模式，取值与传输模型一致，为 `all | any`。自动化编辑页在条件列表上方提供两个选择：

- 满足全部条件（和）
- 满足任一条件（或）

单条件规则仍保存组合模式，但界面可以弱化组合提示。两个及以上条件时，条件行之间应明确展示“且”或“或”。编辑历史数组规则时默认回填“满足全部条件”。

自动化卡片摘要不再只暗示第一项条件，应显示类似“全部满足 · 2 个条件”或“任一满足 · 3 个条件”。具体条件标签继续复用现有设备能力和条件标签映射。

ArkTS 实现应使用显式接口和类型化局部变量，避免在敏感路径引入宽松对象字面量或依赖普通 TypeScript 的写法。

## 后端运行时设计

运行时规则从单个 `trigger` 扩展为一个规范化条件组。规则加载时保留所有条件，不再丢弃第二项及后续条件。

### 规则唤醒

设备或传感器事件到达时，只评估至少包含一个相关条件的规则。“相关”指事件类型和设备标识能够对应规则中的某条条件。无关事件继续快速跳过。

时间规则继续由 `TimeTriggerAdapter` 唤醒，并且只评估其时间配置。

### 状态上下文

评估设备或传感器条件前，运行时构造一致的状态上下文：

1. 本次变化设备优先采用事件的 `after` 状态，确保评估看到触发后的值。
2. 同一条件组中的其他设备通过现有设备状态存储读取当前状态。
3. 如果事件只带部分 `after` 字段，则缺少字段回退到该设备的当前完整状态；事件值覆盖存储值。
4. 找不到设备或目标属性时，该条件按 `false` 处理，并返回可记录的状态不可用原因，不抛出导致整个事件分发中断的异常。

状态解析应以小型、可替换的读取接口注入评估器或运行时，使规则比较逻辑可以独立测试，也使集成测试能够提供确定的设备快照。

### 布尔求值

每个叶子条件继续复用现有布尔、数值和字符串比较语义：

- 布尔值支持真实布尔值以及兼容的 `true/false/on/off` 表示。
- 数值支持 `==`、`>`、`<`、`>=`、`<=`。
- 字符串只支持明确的相等比较。

`all` 对所有条件使用全称判断；任何条件为 `false` 或状态不可用时不执行。`any` 对所有条件使用存在判断；任一条件成立即可执行。空条件组在入口校验阶段被拒绝，运行时遇到历史脏数据时按不匹配处理。

### 动作与保护

条件组成立后继续使用现有 `ActionExecutor` 顺序执行动作。本次保留：

- 同一自动化自触发阻断。
- 最大链深限制。
- 现有动作错误传播和日志记录边界。

布尔条件组不改变动作顺序，也不引入并行动作。

## 错误与日志

运行时结果至少区分：

- `TRIGGER_TYPE_MISMATCH` 或事件与条件组无关。
- `TRIGGER_CONDITION_NOT_MET`。
- `CONDITION_STATE_UNAVAILABLE`，并携带可定位的设备或属性信息。
- 动作执行成功。
- 动作执行失败或动作执行器未配置。

与现有行为一致，无关规则不应产生大量噪声日志。相关规则被实际评估但状态不可用或条件不满足时，可记录跳过原因；成功或失败动作必须保留执行日志。

## 数据流

完整链路为：

1. 用户或演示入口改变设备状态。
2. 现有触发适配器发布设备状态或传感器事件。
3. 自动化运行时筛选包含相关条件的已启用规则。
4. 状态解析器合并事件后的状态与其他设备的当前状态。
5. 规则评估器逐项比较，并按 `all` 或 `any` 聚合。
6. 条件组成立时，动作执行器顺序执行设备命令或场景动作。
7. 执行日志服务记录结果。
8. 测试通过设备查询接口或状态存储确认目标设备状态确实改变。

## 验证策略

### 规则单元测试

覆盖：

- `all` 的全部成立和任一不成立。
- `any` 的任一成立和全部不成立。
- 布尔、数值和字符串比较。
- 设备不存在、属性不存在和部分事件状态合并。
- 历史数组自动归一化为 `all`。
- 空条件组和非法逻辑值的防御行为。

### 运行时集成测试

建立至少两个设备的确定状态快照，派发其中一个设备的变化事件。测试必须证明：

- 事件设备使用 `after` 值。
- 第二个设备从当前状态存储读取。
- `all` 只有在两个设备条件均成立时调用动作执行器。
- `any` 在任一设备条件成立时调用动作执行器。
- 无关设备事件不执行规则。

### 后端端到端测试

通过真实后端服务边界执行一条成功链路：

1. 创建并启用包含两个条件的自动化规则。
2. 预置另一个条件设备的当前状态。
3. 通过现有命令或演示入口改变触发设备状态。
4. 等待自动化动作完成。
5. 查询目标设备，断言动作产生预期状态变化。
6. 查询 `automation_execution_logs`，断言对应执行记录成功。

另加一条反例：第二个 `all` 条件不成立时，目标设备状态不改变，且规则记录为条件未满足或没有成功执行记录。

### 编译与回归边界

若修改 ArkTS 编辑器或映射代码，运行应用模块 `UnitTestBuild`。若只需后端证明，后端采用聚焦自动化测试后再运行 control-center 测试和类型检查。最终报告分别列出：

- 后端单元与集成验证结果。
- 后端端到端副作用和日志验证结果。
- ArkTS/hvigor 编译结果。
- 未执行的模拟器、真机、HAP 安装和涂鸦云端验证。

## 验收标准

- 用户可以为多条件自动化选择“满足全部”或“满足任一”。
- 保存、读取和编辑后组合模式及全部条件保持不变。
- 历史数组规则无需数据迁移即可继续工作，并按 `all` 解释。
- 跨设备 `all` 使用其他设备的当前状态进行判断。
- 条件成立时自动化动作确实改变目标设备状态并留下成功日志。
- 条件不成立时目标设备不发生自动化副作用。
- 自触发与链深保护保持有效。
- 相关后端测试、类型检查以及涉及 ArkTS 时的 `UnitTestBuild` 通过，或明确报告环境阻塞。
