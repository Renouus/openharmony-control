# 自动化加密迁移兼容性设计

## 背景

现有数据库包含历史数组形式的多条件自动化，例如第一条为定时条件、后续为设备状态条件。自动化运行时能够把历史数组按 `all` 条件组读取，但加密持久化校验器按整条记录的 `trigger_type` 为所有条件选择同一种结构校验，导致合法历史记录在加密迁移前被误判为损坏，控制中心无法启动。

## 目标

- 保留现有房间、设备、场景和自动化数据，不删库、不重建规则。
- 保持触发适配器路由可靠：第一条条件必须与记录的 `trigger_type` 匹配。
- 允许后续条件为受支持的时间、设备状态或传感器条件，使加密校验与运行时条件组语义一致。
- 继续拒绝空条件组、未知触发类型、非法字段和损坏密文。
- 保持历史数组按 `logic: all` 解释，不在迁移时重写其业务语义。
- 兼容 ArkTS 历史编辑器写入的空字符串占位字段；只在结构校验时忽略这些空值，密文仍保存原始 JSON。

## 设计

`AutomationEncryptedFields` 仍先执行现有传输归一化。校验器将条件校验拆为两层：

1. 所有条件都必须匹配受支持条件结构的联合类型。
2. 第一条条件必须匹配 `trigger_type` 对应的条件结构，以确保 `TimeTriggerAdapter`、设备状态触发器或传感器触发器注册到正确入口。

数组和 `{ logic, conditions }` 两种载荷都使用相同规则。编码和解码共用这条校验路径，因此迁移成功后的服务启动不会再次拒绝同一条记录。

不在迁移器中增加“跳过校验”开关，也不自动删除、拆分或改写现有自动化。
空字符串兼容仅作用于条件和动作记录的顶层字段。非空未知字段、缺失必填字段以及嵌套命令载荷中的值不会被清理或放宽。

## 错误处理与迁移

迁移流程保持 fail-closed：任何条件无法通过联合结构校验，或第一条条件与 `trigger_type` 不匹配时，dry-run 和写迁移都停止并报告记录位置。写迁移继续使用现有的独占事务、迁移前明文备份和失败回滚机制。

## 测试与验收

- 新增回归测试，复现 `trigger_type=time` 且条件为“定时 + 设备状态”的历史数组，修复前必须失败，修复后可完成 dry-run 和写迁移。
- 覆盖第一条条件与 `trigger_type` 不匹配仍被拒绝。
- 运行加密迁移与自动化相关测试，再运行 control-center 全量测试和类型检查。
- 对当前 `smarthome.db` 先执行 dry-run，再执行带备份写迁移。
- 最后以本机 demo 配置真实启动服务并验证 `/health` 返回成功；旧明文备份保留到验证完成。
